# 第二部分 第九章 关于涉及计算机程序的发明专利申请审查的若干规定

## 核心要点
本章教审查员对涉及计算机程序（含人工智能、"互联网+"、大数据、区块链、商业方法）的申请做两道客体筛查——先按法25.1(2)排除纯智力活动规则，再按法2.2"技术问题—技术手段—技术效果"三要素判断是否构成技术方案；并规定算法特征/商业规则和方法特征何时与技术特征"作为一个整体"进入新颖性、创造性审查，以及流程图、程序模块构架、存储介质/程序产品等特殊撰写要求。

## 审查标准与框架

- **计算机程序本身 vs 涉及计算机程序的发明**（§1）：
  - 计算机程序本身：为了能够得到某种结果而可以由计算机等具有信息处理能力的装置执行的代码化指令序列，或可被自动转换成代码化指令序列的符号化指令序列/符号化语句序列；包括源程序和目标程序。
  - 涉及计算机程序的发明：全部或部分以计算机程序处理流程为基础，通过计算机执行按该流程编制的程序，对**外部对象**（控制外部运行过程或装置、处理或交换外部数据）或**内部对象**（改进系统内部性能、管理内部资源、改进数据传输）进行控制或处理的解决方案；并不必须包含对计算机硬件的改变。审查针对每项权利要求所限定的解决方案（§2）。

- **第一道筛查：智力活动的规则和方法**（§2，法25.1(2)，参照第一章§4.2）：
  - 权利要求仅仅涉及算法或数学计算规则、计算机程序本身、仅仅记录在载体（磁盘、光盘、ROM 等）上的程序本身、游戏的规则和方法等，或除主题名称之外限定的全部内容仅仅涉及上述内容（"实质上仅仅涉及"）→ 不属于客体。典型：仅由所记录的程序本身限定的计算机可读存储介质或计算机程序产品；仅由游戏规则限定、不包括任何物理实体特征的计算机游戏装置。例外：介质涉及物理特性的改进（叠层构成、磁道间隔、材料）→ 不属此列。
  - 限定内容既含智力活动规则又含技术特征 → 就整体而言不是智力活动规则，不应依据法25排除，转入法2.2审查。

- **第二道筛查：技术方案三要素**（§2，法2.2）：同时满足 (a) 执行程序的**目的是解决技术问题**；(b) 运行程序对外部/内部对象进行控制或处理所反映的是**遵循自然规律的技术手段**；(c) 由此获得**符合自然规律的技术效果** → 技术方案；任一不满足 → 不属于客体。三类典型可授权路径：①工业过程、测量或测试过程控制（例4 橡胶硫化控制、例7 粘度测量）；②处理外部技术数据（例6 图像去噪）；③改善计算机系统内部性能（例5 虚拟设备文件系统扩充存储）。

- **汉字编码方法 / 计算机汉字输入方法**（§4，法25.1(2)）：编码方法是信息表述方法——问题仅取决于人的表达意愿、手段仅是人为规定的编码规则、结果仅是符号/字母数字串 → 智力活动规则。编码方法与其可使用的**特定键盘**相结合，使计算机能以汉字信息为指令运行程序 → 技术方案；撰写时描述输入方法的技术特征，必要时描述键盘各键位的定义及位置。

- **说明书撰写**（§5.1，法26.3）：必须清楚、完整地描述程序的**设计构思、技术特征及达到技术效果的实施方式**；附图给出主要**流程图**，说明书按流程时间顺序以自然语言描述各步骤；充分程度以本领域技术人员能据流程图及说明**编制出能达到所述技术效果的程序**为准。可简短摘录关键源程序，不需要提交全部源程序。含硬件结构改变的，附图给出硬件实体结构图并描述各硬件组成部分及相互关系。

- **权利要求书撰写**（§5.2，法26.4、细则20.2）：
  - 可写成方法权利要求，或产品权利要求（实现该方法的装置、计算机可读存储介质、计算机程序产品）。任何形式都必须得到说明书支持、从整体上反映技术方案、记载解决技术问题的**必要技术特征**，不能只概括描述程序的功能及其效果。方法权利要求按流程步骤详细描述程序执行的各项功能以及**如何完成**；装置权利要求具体描述各组成部分及其关系，组成部分可包括硬件，也可包括程序。
  - **程序模块构架规则**：装置权利要求全部以程序流程为依据、各组成部分与流程各步骤（或方法权利要求各步骤）完全对应一致 → 各组成部分理解为实现各步骤所必须建立的**程序模块**，该权利要求理解为主要通过说明书记载的程序实现方案的程序模块构架，而非主要通过硬件实现的实体装置。计算机程序产品理解为主要通过程序实现方案的软件产品。§5.2 例4 示范同一方法配套的装置（存储器+处理器+程序）、存储介质、程序产品三种产品权利要求写法，均以"被处理器执行时实现权1步骤"限定。

- **含算法特征或商业规则和方法特征的申请：整体分析原则**（§6.1）：不应简单割裂技术特征与算法特征或商业规则和方法特征，应将权利要求记载的所有内容作为一个整体，分析其技术手段、技术问题和技术效果。法25.1(2)（§6.1.1）：涉及抽象的算法或单纯的商业规则和方法**且不包含任何技术特征** → 排除（不含技术特征的抽象数学模型建立方法；特征全部为返利规则的返利方法）；含任何技术特征 → 不应依法25.1(2)排除。

- **法2.2 审查的三条认定路径**（§6.1.2）：整体考虑全部特征，记载了对技术问题采用利用自然规律的技术手段并获得符合自然规律的技术效果 → 技术方案。具体：
  1. 算法各步骤与技术问题密切相关：处理的数据是技术领域中**具有确切技术含义的数据**，算法执行直接体现利用自然规律解决技术问题的过程并获得技术效果 → 通常属于技术方案（例2 CNN 训练处理图像数据；例7 知识图谱推理处理自然语言文本）。
  2. 深度学习、分类、聚类等 AI/大数据算法的改进，与**计算机系统内部结构存在特定技术关联**，解决提升硬件运算效率或执行效果（减少数据存储量、减少数据传输量、提高硬件处理速度等）的技术问题 → 技术方案（例5 按训练数据大小选取单/多处理器训练方案）。
  3. 处理**具体应用领域**的大数据，用分类、聚类、回归分析、神经网络等挖掘**符合自然规律的内在关联关系**，解决提升该领域大数据分析可靠性或精确性的技术问题 → 技术方案（例6 电子券使用倾向度）。反例：例10 金融价格预测——价格走势遵循经济学规律，历史与未来价格间不存在符合自然规律的内在关联，不构成技术问题。

- **新颖性**（§6.1.3，法22.2）：考虑权利要求记载的**全部特征**，既包括技术特征，也包括算法特征或商业规则和方法特征。

- **创造性：整体考虑规则**（§6.1.3，法22.3）：将与技术特征**"功能上彼此相互支持、存在相互作用关系"**的算法特征/商业规则和方法特征与技术特征作为一个整体考虑。该短语指二者紧密结合、共同构成解决某一技术问题的技术手段，并能获得相应技术效果。认定情形：
  - 算法应用于具体技术领域、可解决具体技术问题 → 算法特征成为技术手段的组成部分，考虑其贡献；
  - 算法与计算机系统内部结构存在特定技术关联，改进内部性能、提升硬件运算效率或执行效果 → 考虑其贡献（例15 按硬件使用率填充神经网络权重参数尺寸）；
  - 商业规则和方法特征的实施**需要技术手段的调整或改进** → 考虑其贡献；
  - 用户体验提升由技术特征带来，或由技术特征与相互支持的算法/商业规则特征共同带来 → 予以考虑（例13 批量取件通知迫使服务器与终端间数据架构、通信方式调整）。

- **含算法/商业规则特征申请的撰写**（§6.3，法26.3、26.4）：说明书写明技术特征与相互支持的算法/商业规则特征**如何共同作用并产生有益效果**；含算法特征时，**至少一个输入参数及其相关输出结果的定义应与技术领域中的具体数据对应关联**；含商业规则特征时，详细描述解决技术问题的整个过程至本领域技术人员能够实现。有益效果写质量、精度或效率的提高、系统内部性能的改善等；写用户体验提升时须同时说明其如何由上述特征共同带来。权利要求记载技术特征以及与其相互支持的算法/商业规则和方法特征。

## 关键概念
- **计算机程序本身**：可由信息处理装置执行的代码化指令序列或可自动转换为其的符号化指令/语句序列，含源程序与目标程序（§1）。
- **外部对象 / 内部对象**：外部运行过程、外部装置、外部数据 / 系统内部性能、内部资源、数据传输（§1）。
- **智力活动的规则和方法**：算法、数学计算规则、程序本身、游戏规则、编码规则等仅取决于人的思维或人为规定的内容（§2，法25.1(2)）。
- **技术方案三要素**：技术问题、遵循自然规律的技术手段、符合自然规律的技术效果（§2，法2.2）。
- **功能上彼此相互支持、存在相互作用关系**：算法/商业规则特征与技术特征紧密结合、共同构成解决某一技术问题的技术手段并获得技术效果（§6.1.3）。
- **具有确切技术含义的数据**：像素灰度、传感器信号、文本语义等承载技术意义的数据，是算法与技术问题密切相关的标志（§6.1.2）。
- **符合自然规律的内在关联关系**：大数据挖掘所得、非由人为规定或经济学规律决定的关联（§6.1.2）。
- **程序模块构架**：各组成部分与程序流程步骤一一对应的装置权利要求，理解为程序模块而非硬件实体（§5.2）。

## 思维模型
1. 两道门依次过：先问"除主题名称外的限定内容是否**仅仅**是算法/程序/规则"（法25.1(2)）；只要含任一技术特征就进第二道门，逐一核对技术问题、技术手段、技术效果（法2.2），缺一不可。
2. "由计算机执行"不是技术手段的充分条件：把公知计算机看作透明容器，看程序对对象的控制或处理本身是否遵循自然规律；手段和效果若由人为规定（游戏、编码、返利规则）或经济学规律决定，仍是智力活动（例8 游戏：装置公知，内部性能与构成均无改变）。
3. 判断算法是否"落地"看三处：数据有无确切技术含义、是否针对具体应用领域、是否触及计算机内部结构——任一成立即可能构成技术方案；三者皆无即抽象算法。
4. 创造性中做"替换测试"：换掉该规则/算法而技术手段无需改变（例14 情感分类规则）→ 不相互支持，不计入贡献；规则的实施迫使数据架构或通信方式调整（例13）→ 整体考虑。

## 反模式
- **仅由程序限定的存储介质/程序产品权利要求**：实质上仅涉及智力活动规则，法25.1(2) 排除；只有介质物理特性改进才能绕开（§2）。
- **主题名称加"计算机"却全是人为规则或经济规律**：例3 全球语言转换（自定义录入/标词规则）、例8 游戏方法、§6.2 例8 消费返利、例9 经济景气指数——问题不构成技术问题、手段不受自然规律约束。
- **数值计算披上物理量外衣**：例2 用计算机按公式算动摩擦系数——不是对测量方法的改进，整体仍是数学计算方法（法25.1(2)）。
- **权利要求只概括功能与效果**：不记载步骤如何完成或装置组成及关系 → 缺必要技术特征、得不到说明书支持（法26.4、细则20.2）。
- **说明书无流程图或只堆源代码**：本领域技术人员无法据以编制程序 → 公开不充分（法26.3）；AI 申请输入输出参数未与技术领域具体数据关联同理。
- **创造性中割裂特征**：审查员剥离算法/商业规则特征后只比技术特征违反§6.1整体原则；申请人把与技术手段不相互作用的规则当作区别特征主张贡献不被认可（例14）。

## 实例演练
**客体正反对照**：§3 例6 图像去噪——将灰度落在全图均值±3倍方差外的像素判为噪声修改，其余不动。技术问题：去噪同时减少模糊；手段：基于具有技术含义的像素灰度统计量处理；效果：噪声去除、模糊减少、运算量下降 → 属于客体。对照 §6.2 例1 建立数学模型——用相关分类任务的样本扩充训练特征提取模型再训练分类模型：特征值、标签、模型均为抽象通用数据，无任何应用领域和技术特征 → 法25.1(2) 排除。分水岭：数据是否具有确切技术含义、是否与具体领域结合。

**创造性正反对照**：例11 仿人机器人跌倒检测——区别在于用模糊决策算法融合姿态、ZMP、步行阶段传感器信息判定稳定性，输出用于姿势调整指令 → 算法与技术特征相互支持；实际解决的技术问题重新确定为"如何判断机器人稳定状态并准确预测跌倒方向"，该算法及其应用未被公开、非公知常识 → 具备创造性。例14 动态观点可视化——区别仅为情感分类规则，着色手段无需随规则改变 → 不相互支持，未解决技术问题，不具备创造性。例12 多机器人路径规划——算法与技术特征相互支持，但对比文件2已给出用 Messy 遗传算法优化路径的启示 → 仍显而易见（相互支持≠自动具备创造性）。

## 关键要点
1. 客体审查按"法25.1(2) → 法2.2"两步走，针对每项权利要求限定的整体方案，不割裂特征；技术方案须同时确认技术问题、遵循自然规律的技术手段、符合自然规律的技术效果。
2. 工业/测量过程控制、外部技术数据处理、内部性能改进是三类安全港。
3. AI/大数据方案的可授权抓手：数据具有确切技术含义；或算法与计算机内部结构特定关联、提升硬件效率；或挖掘具体领域中符合自然规律的关联。经济、金融、返利、游戏规则不是。
4. 新颖性考虑全部特征；创造性只把"功能上彼此相互支持、存在相互作用关系"的算法/商业规则特征纳入整体，标准是该特征是否成为解决技术问题的技术手段的组成部分。
5. 说明书必须有主要流程图和按时间顺序的自然语言步骤描述，达到本领域技术人员能编制出程序的程度；AI 申请至少一个输入参数及输出结果须与技术领域具体数据关联。
6. 权利要求可写方法、装置、存储介质、程序产品，均须记载必要技术特征；与流程步骤一一对应的装置权利要求按程序模块构架理解；主张用户体验提升须说明其由技术特征（及相互支持特征）如何共同带来。
